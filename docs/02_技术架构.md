# 技术架构

## 架构原则

本项目采用“插件侧轻控制 + 云端侧重业务”的方式，并在插件与后端两侧都保持清晰分层。

核心原则：

- 插件入口不直接堆业务逻辑
- 抽卡规则集中在服务层
- 数据访问走仓储层 / API 客户端层
- 数据持久化只由云端后端负责
- AstrBot 插件只负责接入与展示

## 总体分层

### AstrBot 插件侧

- `Controller`
  - 接收 AstrBot 事件与命令
  - 解析参数
  - 调用服务
  - 格式化回复文本
- `Service`
  - 组织命令级业务流程
  - 处理调用后端 API 的业务编排
- `Model`
  - 抽卡请求对象、响应对象、排行对象、用户对象
- `Infrastructure`
  - HTTP 客户端
  - 配置读取
  - 时间工具
  - 日志封装

### 云端后端侧

- `Controller / Router`
  - 对外提供 HTTP API
- `Service`
  - 每日次数校验
  - 抽卡逻辑
  - 排行聚合
  - 管理操作
- `Repository`
  - 访问 MySQL
- `Model / Schema`
  - 数据表实体
  - 请求响应 DTO

## 插件入口职责

`main.py` 后续应该只保留三类内容：

- AstrBot 插件注册
- 配置初始化
- 控制器装配与命令分发

不建议在 `main.py` 中直接出现：

- 复杂抽卡概率逻辑
- MySQL SQL 语句
- 排行统计实现
- 管理命令的大量字符串分支

## MVC 责任边界

### Controller

负责：

- 识别命令
- 获取 QQ 号、群号、管理员身份
- 处理参数错误提示
- 组织回复文本

不负责：

- 概率抽卡
- 配额计算
- 数据库存取

### Service

负责：

- 单抽 / 十连的业务编排
- 每日次数扣减策略
- 排行查询口径
- 管理动作校验

### Repository / API Client

负责：

- 对接云端 MySQL API
- 统一处理请求超时、鉴权、错误码
- 将原始响应转换为插件内部 DTO

## 为什么不用插件直连 MySQL

当前方向明确为 `MySQL API`，因此插件不直接访问数据库更合适，原因如下：

- AstrBot 插件部署位置可能分散，数据库凭据不适合散落在多个机器人实例中
- 后端可以集中处理权限、限流、日志和统计聚合
- 后续若要接网页管理台，可以直接复用同一套 API

## AstrBot 约束

AstrBot 官方文档要求插件通过 `metadata.yaml` 提供元数据，并通过 `_conf_schema.json` 注册可视化配置；插件依赖则使用 `requirements.txt` 管理 [$TRAE_REF](https://docs.astrbot.app/dev/star/plugin-new.html)[$TRAE_REF](https://docs.astrbot.app/dev/star/guides/plugin-config.html)。

因此本项目后续必须重写当前复制来的：

- `metadata.yaml`
- `_conf_schema.json`
- `README.md`
- `requirements.txt`

避免继续保留“消息防抖插件”的语义与依赖。
