# 需求与范围

## 用户侧需求

面向普通 QQ 用户，第一版需要支持以下能力：

### 抽卡能力

- 每日抽卡
  - 每个 QQ 按自然日判断次数
- 支持单抽
- 支持十连
- 支持指定卡池抽取

### 查询能力

- 查询自己今日抽卡结果
- 查询自己的历史抽卡记录
- 查询自己的累计统计
- 查询抽卡排行榜

### 反馈能力

- 抽卡结果文本需要有明确的结构化反馈：
  - 卡池名称
  - 抽取模式
  - 抽卡时间
  - 卡牌列表
  - 稀有度统计
  - 剩余可用次数或次日刷新说明

## 管理侧需求

第一版管理员需要具备以下能力：

- 创建卡池
- 启用 / 停用卡池
- 配置卡池基础信息
  - 名称
  - 描述
  - 每日次数规则
  - 开放模式
- 创建卡牌
- 编辑卡牌稀有度与权重
- 把卡牌加入指定卡池
- 查看指定 QQ 的抽卡记录
- 重置指定 QQ 的每日次数
- 查看排行榜统计

## 排行统计范围

第一版建议至少包含：

- 今日榜
- 总榜
- 可选榜单维度：
  - 抽卡次数
  - 高稀有卡数量
  - 欧气积分

其中“欧气积分”建议作为主榜值，便于统一不同稀有度与不同模式的统计口径。

示例积分建议：

- N：1 分
- R：2 分
- SR：5 分
- SSR：12 分
- UR：20 分

该积分配置应后续允许后台调整，但第一版可先写入后端配置表或常量表。

## 业务规则建议

### 每日次数

由于你选择了多模式，第一版建议将次数设计为两层：

- `daily_single_quota`
- `daily_ten_draw_quota`

而不是简单共享一个总次数字段。原因是后续扩展活动池、节日池时更稳定，也更容易解释给用户。

### 十连规则

第一版建议默认：

- 十连是独立模式
- 是否允许每日十连，由卡池配置决定
- 十连暂不引入保底

原因是这样能先把系统骨架搭稳，避免在第一版把概率状态机做得过重。

### QQ 识别口径

本项目按 QQ 全局统计，因此识别用户时：

- 主键使用 QQ 号
- 群号仅作为行为上下文记录
- 不作为每日抽卡资格的隔离维度

## 第一版必须完成

- AstrBot 命令入口
- 用户身份提取与 QQ 号归档
- 单抽 / 十连
- 卡池与卡牌配置
- 云端 API 调用
- MySQL 持久化
- 今日结果查询
- 历史记录查询
- 排行榜查询
- 管理员维护命令
- 基础异常处理与日志

## 第一版暂缓

- 卡面图片渲染
- 前端 Web 管理台
- 跨平台账号体系
- 保底继承
- 卡牌碎片、兑换、仓库系统
- 群排行与跨群活动
- 自动定时活动池切换

## 验收标准

第一版完成后，至少要满足以下场景：

1. 用户使用命令成功单抽或十连。
2. 相同 QQ 在同一天内再次抽卡时，能正确判断剩余次数。
3. 后端 MySQL 中能看到抽卡记录与汇总数据。
4. 用户可查询今日结果和历史记录。
5. 管理员可通过命令维护卡池与卡牌。
6. 排行榜能按配置口径输出前 N 名。
