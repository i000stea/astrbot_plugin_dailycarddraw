# 开发顺序

## 第一阶段

先完成项目骨架清理与目录落位：

- 重写 `metadata.yaml`
- 重写 `_conf_schema.json`
- 移除不再需要的防抖相关依赖
- 新建 `app/` 分层目录
- 保留 `main.py` 作为 AstrBot 插件入口

阶段目标：

- 当前项目从“被复制的参考插件”变成“抽卡插件工程骨架”

## 第二阶段

完成插件侧基础 MVC：

- 命令入口
- 控制器拆分
- API 客户端
- 响应格式化器
- 管理员鉴权

阶段目标：

- 插件可接收抽卡 / 查询 / 管理命令，并能请求后端 API

## 第三阶段

完成云端后端服务：

- MySQL 连接
- 数据表建模
- 抽卡服务
- 每日配额服务
- 管理接口

阶段目标：

- 插件的所有主要功能均可通过后端接口正常工作

## 第四阶段

联调与验证：

- 用户单抽
- 用户十连
- 今日次数限制
- 历史记录
- 累计统计
- 管理员卡池配置

阶段目标：

- 在真实 AstrBot 环境中完成最小闭环验证

## 当前推荐先做的实现内容

基于你现在的要求，我建议下一轮正式开发优先做：

1. 清理根目录参考插件语义
2. 搭建插件 `app/` 分层
3. 设计并创建后端目录骨架
4. 输出第一版数据库建表 SQL
5. 重写插件配置项
6. 写一个最小可通的“抽卡”命令到假后端或本地 mock

这样做的好处是：

- 可以先把系统边界跑通
- 不会一上来就陷入复杂概率细节
- 后续你要改规则时，调整成本低

## 风险点

当前最大的方向性风险有三个：

1. 十连与每日限制的业务口径是否最终固定。
2. 后端 MySQL API 是否有你现成服务环境可直接部署。
3. AstrBot 命令风格是否要兼容你已有其他插件的交互习惯。

如果这三个点后面发生变化，受影响最大的是：

- `03_数据模型与云端接口.md`
- `04_命令与管理接口.md`

## 进入正式开发前的确认点

建议你下一步重点确认：

1. 十连是否独立消耗次数
2. 是否需要“默认卡池”
3. 管理命令是否接受纯文本格式
4. 云端后端是否由我在本项目内一并搭建 Python 服务骨架
